# Project X — студия персональных печатных подарков

Одна платформа, три продукта на своих доменах:

| Продукт | Домен | Что это | Чек |
|---|---|---|---|
| **Cover Me** (`glossy`) | coverme.kz | Глянцевый журнал A4 на 24–36 страниц про человека, пару или компанию | 10 000 ₸ предоплата → 25 000–35 000 ₸ |
| **Шежіре** (`shezhire`) | shezhire.kz | Книга рода, древо семьи, реставрация архивных фото, постер или холст | 10 000 ₸ → 45 000–80 000 ₸ |
| **MyGame** (`boardgame`) | mygame.kz | Настольная игра про компанию: карты конфликта, викторина или «своя экономическая» | 10 000 ₸ → 30 000–45 000 ₸, B2B от 150 000 ₸ |

Сценарий у всех трёх общий:
1. Заказчик выбирает формат и допы, вносит предоплату.
2. Заполняет анкету и рассылает ссылку-приглашение в WhatsApp, чтобы друзья, родные или коллеги добавили свои истории и фото.
3. Отправляет материалы. ИИ собирает черновик текстов, сервис layout сам верстает печатный макет.
4. Заказчик смотрит макет в кабинете: согласует и оплачивает остаток или просит правки (ИИ переписывает, макет пересобирается). После лимита правок заказ берёт дизайнер студии. Дальше печать и доставка.

Разница между продуктами — только в данных (форматы, цены, вопросы анкеты) и в оформлении. Код у них общий.

## Архитектура

Один репозиторий, без монорепо-инструментов: каждый пакет — самостоятельный npm-проект со своим `package.json` и lock-файлом. Общий код подключается обычной зависимостью `file:`.

```
                 ┌─────────────────────────┐
  браузер ──────▶│ frontend (Next.js 16)   │  coverme.kz · shezhire.kz · mygame.kz · хаб
                 └───────────┬─────────────┘
                             │ HTTP /api/*
                 ┌───────────▼─────────────┐
                 │ gateway                 │  единственная публичная точка API:
                 │                         │  маршрутизация, CORS, rate limit, admin-токен
                 └─┬───────┬────────┬────┬─┘
        ┌──────────┘       │        │    └─────────┐
┌───────▼──────┐ ┌─────────▼───┐ ┌──▼─────────┐ ┌──▼──────┐
│ catalog      │ │ projects    │ │ payments   │ │ media   │
│ продукты,    │ │ заказы,     │ │ платежи,   │ │ фото,   │
│ цены, анкеты │ │ анкеты,     │ │ провайдеры,│ │ хранилище│
│ (без БД)     │ │ приглашения │ │ webhooks   │ │ (диск/S3)│
└──────────────┘ └──┬───────▲──┘ └──┬─────────┘ └─────────┘
          HTTP ◀────┘       │       │ Postgres px_payments
     (catalog, payments)    │       │
            Postgres        │       │
           px_projects      │       │
                 ┌──────────┴───────▼──────────┐      ┌─────────────┐
                 │ NATS JetStream (события)    │◀────▶│ ai          │
                 └──────────────▲──────────────┘      │ черновики   │
                                │                     │ (Claude)    │
                         ┌──────┴──────┐              └─────────────┘
                         │ layout      │ PDF-макет и превью страниц:
                         │ вёрстка     │ HTTP в projects (материалы), media (фото, файлы)
                         └─────────────┘
```

### Принципы

- **У каждого сервиса своя база.** projects и payments владеют каждый своей базой Postgres, в чужие никто не ходит. catalog, media и ai хранят состояние без собственной БД.
- **Синхронно — только то, без чего не ответить пользователю.** projects ходит в catalog за анкетой и в payments за ссылкой на оплату. Остальное идёт через события.
- **Transactional outbox.** Изменение состояния и событие о нём записываются в одной транзакции, а relay публикует события в NATS. Событие не теряется и не уходит для отменённой транзакции. Relay использует `FOR UPDATE SKIP LOCKED`, поэтому сервис можно масштабировать на несколько реплик.
- **Идемпотентные подписчики.** JetStream доставляет событие минимум один раз, а таблица `processed_events` гарантирует, что событие применится ровно однажды. Повторный webhook или повторная доставка не задвоят оплату.
- **Контракты в одном месте.** `shared/contracts` содержит zod-схемы всех запросов, ответов и событий. Их же использует фронт, поэтому форма валидируется в браузере и на сервере одинаково.
- **Гексагональная структура сервиса.** `domain/` — чистые бизнес-правила без I/O. `application/` — сценарии и порты (интерфейсы). `infrastructure/` — Postgres, HTTP-клиенты, провайдеры. `http/` и `events/` — тонкие адаптеры. Сборка всех частей — в `app.ts`.
- **Анкеты описаны данными.** Вопросы задаются в catalog как схема полей. Фронт рисует по ней форму, projects валидирует ответы, ai превращает их в текст.

### Сервисы

| Сервис | Порт | Хранилище | Ответственность |
|---|---|---|---|
| `gateway` | 8080 | — | Публичный API `/api/*`, маршрутизация, CORS, rate limit, авторизация studio-админки. `/internal/*` наружу не открывается |
| `catalog` | 4101 | — (определения в коде) | Продукты, форматы, допы, анкеты, расчёт цены |
| `projects` | 4102 | Postgres `px_projects` | Заказы, ответы анкеты, вклады приглашённых, жизненный цикл, расчёт суммы к оплате |
| `payments` | 4103 | Postgres `px_payments` | Платёжные сессии, подключаемые провайдеры, webhooks |
| `media` | 4104 | диск (интерфейс для S3) | Загрузка фото с проверкой настоящего типа файла, раздача |
| `ai` | 4105 | — | Черновик текстов по материалам и его переписывание по правкам: Claude или шаблонный генератор |
| `layout` | 4107 | — (файлы в media) | Автоматическая вёрстка: печатный PDF по шаблону продукта и SVG-превью страниц, см. `services/layout/README.md` |
| `voice` | 4108 | — | Голосовая студия: выдаёт браузеру сессию разговора с агентом ElevenLabs и инструктирует его анкетой заказа, см. `services/voice/README.md` |
| `frontend` | 3000 | — | Три брендовых сайта, хаб, кабинет заказа, приглашения, студийная админка |

### События

| Событие | Публикует | Слушает | Зачем |
|---|---|---|---|
| `payments.succeeded` | payments | projects | Учесть оплату: `draft → deposit_paid`, `awaiting_approval → paid` |
| `projects.submitted` | projects | ai | Материалы отправлены — сгенерировать черновик |
| `ai.draft_generated` | ai | projects, layout | Сохранить черновик; сверстать по нему макет |
| `layout.generated` | layout | projects | Новая версия макета: `in_design → awaiting_approval`, макет в кабинете |
| `layout.failed` | layout | projects | Вёрстка не удалась после повторов: заказ уходит дизайнеру студии |
| `projects.revision_requested` | projects | ai | Заказчик просит правки: переписать черновик с учётом комментария |
| `projects.layout_approved` | projects | (уведомления) | Заказчик согласовал макет, дальше оплата остатка |
| `projects.design_handoff` | projects | (уведомления) | Автоматика остановилась (лимит правок, сбой): нужен дизайнер |
| `projects.status_changed` | projects | (уведомления, аналитика) | Точка расширения: WhatsApp/SMS, CRM |

### Жизненный цикл заказа

```
draft ──предоплата──▶ deposit_paid ──отправка──▶ in_design ──макет готов──▶ awaiting_approval
                                                     ▲                            │ «Согласовать»
                                                     └──── «Нужны правки» ────────┤
                                                                                  ▼ оплата остатка
                      delivered ◀── shipped ◀── printing ◀─────────────────────── paid
```
Макет из `in_design` в `awaiting_approval` переводит событие `layout.generated`. Правки возвращают заказ в `in_design`
и запускают новый круг ИИ и вёрстки. После `LAYOUT_REVISION_LIMIT` кругов (по умолчанию 3) или сбоя вёрстки заказ
переходит в режим `studio`: дизайнер доводит макет и сам ставит `awaiting_approval` в `/admin`. Оплата остатка
открывается только после согласования автоматического макета.
Статусы `deposit_paid` и `paid` выставляются только платежами, вручную их не поставить. Переходы описаны в `shared/contracts/src/projects.ts`, правила — в `services/projects/src/domain/project.ts`.

## Запуск

### Весь стек в Docker

```bash
cp .env.example .env          # задайте ADMIN_TOKEN и ADMIN_PASSWORD
docker compose up --build
```

- сайты: http://localhost:3000 (хаб), http://localhost:3000/glossy, `/shezhire`, `/boardgame`
- API: http://localhost:8080/api/catalog/products
- админка студии: http://localhost:3000/admin (логин и пароль из `.env`)
- мониторинг NATS: http://localhost:8222

Оплата по умолчанию идёт через тестового провайдера `mock`: после нажатия «Оплатить» открывается тестовая страница оплаты.

Браузер ходит в API только через фронтенд (`/api/*` того же домена), а фронтенд передаёт IP клиента в `X-Forwarded-For`. Поэтому в проде держите gateway в приватной сети за фронтендом или балансировщиком (`TRUST_PROXY=true`). Порт 8080 в compose открыт только для локальной отладки. Наружу должны смотреть только webhooks платёжных систем: `/api/webhooks/payments/*`.

### Прод

Стенд на общем сервере рядом с MyBooks и DoseWear: https://px.185.102.75.191.sslip.io (хаб и `/admin`), бренды на `coverme.`, `shezhire.`, `mygame.185.102.75.191.sslip.io`. PM2, Kaspi Pay через общий kaspi-pos, фото в S3. Как устроено и как выкатывать — `deploy/README.md`.

### Локальная разработка

```bash
make install                  # npm install во всех пакетах
make infra                    # Postgres + NATS в Docker
cd services/catalog && npm run dev    # и так для каждого нужного сервиса (у каждого свой .env)
cd frontend && npm run dev
```

Каждый сервис читает свой `.env` (образец — `.env.example` рядом). `npm run dev` перезапускает сервис при изменениях, в том числе в `shared/`.

### Проверки

```bash
make typecheck
make test       # unit и интеграционные тесты; projects/payments поднимаются на реальном Postgres
make build
```

В интеграционных тестах сервис поднимается целиком через `app.ts` с реальным Postgres и шиной событий в памяти (`@px/service-kit/testing`). Тест проходит весь путь заказа: создание → вклад приглашённого → предоплата (включая повторную доставку события) → отправка → черновик ИИ → согласование → оплата остатка. Отдельный тест — цикл автоматического макета: `layout.generated` → согласование → оплата, правки → `projects.revision_requested` → лимит → студия.

## Как менять

**Цены, форматы, допы, вопросы анкеты.** Правьте `services/catalog/src/products/<продукт>.ts`. Определения проверяются схемой при старте, поэтому опечатка роняет деплой, а не заказ клиента. Уже оформленные заказы хранят снимок цены и от правок не меняются.

**Добавить четвёртый продукт:**
1. добавьте id в `ProductId` в `shared/contracts/src/products.ts`;
2. создайте `services/catalog/src/products/<id>.ts` и подключите его в `products/index.ts`;
3. добавьте редакторский бриф в `services/ai/src/prompts/instructions.ts`;
4. добавьте бренд во фронтенде (`frontend/src/brands/<id>/`, см. `frontend/README.md`).

**Подключить платёжную систему** (Kaspi Pay, Freedom Pay, CloudPayments): реализуйте интерфейс `PaymentProvider` в `services/payments/src/providers/`, зарегистрируйте его в `providers/index.ts`, выставьте `PAYMENT_PROVIDER`. Webhook придёт на `POST /api/webhooks/payments/<provider>` с исходным телом запроса для проверки подписи.

**Хранилище фото в S3.** Реализуйте интерфейс `Storage` (`services/media/src/storage/storage.ts`) и добавьте значение в `STORAGE_DRIVER`.

**Шаблоны макетов.** `services/layout/src/templates/<продукт>.ts`. `npm run sample` в `services/layout` рисует все три продукта на тестовых данных, `npm run bench` меряет время и память.

**ИИ.** `AI_GENERATOR=claude` и `ANTHROPIC_API_KEY` включают генерацию через Claude (`claude-opus-5-5`, structured outputs, серверный fallback на случай отказа модели). По умолчанию работает `template`: он раскладывает ответы по разделам без внешних вызовов.

**Новый подписчик на событие** (например, уведомления в WhatsApp): создайте сервис на `@px/service-kit` и подпишитесь через `bus.subscribe('projects.status_changed', { durable: '<service>--status-changed' }, handler)`.

---

**Голос редактора.** Тон, правила интервью и инструменты агента — `services/voice/src/agent/` (после правок `npm run provision`).
Сами вопросы берутся из анкеты продукта в каталоге: новое поле сразу появляется и в формах, и в разговоре.
